# Program configuration and service routing

Implementation contract for capability 1 and its admission, scheduling, documentation, billing and leadership connections. This extends the 50-capability objective; it is not a completion claim. The reference is the repository roadmap and inspected Figma Prep specifications. No shipped program, service-code or patient catalog is seeded. Authentication remains deferred and all work stays local.

## Data and administration

Root owns migration `202611020020_program_configuration.sql` and all integration into existing modules. Workers must not edit migrations or existing files outside their explicit assignment.

`care_programs`: id, organization_id, facility_id, code, name, level_of_care (`outpatient|iop|php`), min_age (18..120), max_age (nullable, min_age..130), capacity (1..10000), active, version (starts at 1), created_at, updated_at. Facility, code and care level are immutable; retire and create a different program to change that context. Names, age bounds, capacity and active state may change optimistically. Capacity counts episodes with this program_id and status active; planned intakes do not reserve space. Reject a reduction below active census. Disabling a program blocks new intake/admission/bookings; existing visits, records, discharge and financial history remain usable. Existing patients outside newly edited age bounds keep their already admitted care.

`program_required_forms`: program_id, organization_id, template_id, stage (`intake|discharge`). Program rules add to existing organization stage/care-level requirements. All referenced templates must belong to the organization and be active when configured; duplicate IDs are rejected. Inactive templates that are still referenced must be surfaced as configuration blockers, never silently removed from requirements. Responses must be signed for the same patient/episode and pass existing transcript-source validation.

`program_revisions`: immutable id/org/program_id/version/snapshot/reason/actor_id/created_at. Snapshot is the full configuration plus required intake/discharge template IDs. Every create/update inserts a revision; require an explicit 10..2000-character change_reason. Never store clinical narrative in audit_events. There is no delete endpoint. Revision history is admin-only.

`program_services`: id/org/program_id, code_system (`internal|cpt|hcpcs`), service_code (1..40), name (1..160), session_kind (`individual|group|assessment|family|case_management`), min_minutes, default_minutes, max_minutes (1..480 and min <= default <= max), default_charge_cents (nullable integer 0..100000000), note_template_id (nullable same-org template), active, version, timestamps. Program, code system, code and session kind are immutable. A note template must be active at selection. No licensed terminology data is bundled. A service code here is an organization-authored catalog entry, not proof a payer accepts it. Every service create/update appends an immutable program_service_revision with full snapshot, reason and actor. Catalog changes never rewrite past encounter snapshots.

`episodes.program_id` is nullable only to preserve pre-migration episodes. `sessions.program_service_id` and `groups.program_service_id` are nullable only for retained old bookings; both have `service_snapshot` JSON objects. Root enforces one-time explicit assignment of older episodes to programs. `episode_program_assignments` is append-only (episode/patient/org/program/actor/reason/snapshot/time). Admission transitions also append `intake_decision_evidence` with case, event, patient, episode, current program version/configuration and evaluated checklist, so later rule edits do not rewrite evidence of the decision.

## Catalog API (worker A)

Implement only `api/src/programs/mod.rs`, optional `api/src/programs/catalog.rs`, and focused `api/tests/program_catalog_postgres.rs`. Expose `pub fn configure(cfg: &mut web::ServiceConfig)`; root wires it before generic routes. Root will add sibling modules `services` and `adoptions`, do not declare nonexistent siblings yourself. Do not edit lib/routes/records/access or migration files.

All active staff may read `GET /api/program-catalog`, returning `{programs:[program],services:[service],can_manage:boolean}`. Each program contains all scalar fields, `required_intake_template_ids`, `required_discharge_template_ids`, `active_census`, and `available_places` (nonnegative difference); no patient identities. Bound to 1000 programs and 5000 services; if exceeded fail clearly instead of truncating. All roles need the same operational catalog for selection; no clinical narratives are included. Successful access is audited and no-store. Only active administrators may write or read configuration history; resource exceptions do not expand this. Re-read actor after scheduling::lock_org under the existing org mutation lock.

- POST `/api/care-programs`: `{facility_id,code,name,level_of_care,min_age,max_age,capacity,active,required_intake_template_ids,required_discharge_template_ids,change_reason}` → program view. Require active facility, exact bounded fields/types, no unknown input. Duplicate code unique case-insensitively within organization.
- PATCH `/api/care-programs/{id}`: `{_expected_updated_at,change_reason,name?,min_age?,max_age?,capacity?,active?,required_intake_template_ids?,required_discharge_template_ids?}` → program view. Missing timestamp 428, stale 409. Validate merged fields and replace only supplied form lists atomically. No-op can reject. Changing facility/code/level is forbidden. May activate only under active facility.
- GET `/api/care-programs/{id}/history` → `{revisions:[...]}` newest first, bounded 200; fail if greater.
- POST `/api/program-services`: `{program_id,code_system,service_code,name,session_kind,min_minutes,default_minutes,max_minutes,default_charge_cents,note_template_id,active,change_reason}` → service view. Parent program active, same org, facility active. Required text trimmed, case normalization of program/service code uppercase. Service uniqueness `(program_id,code_system,upper(service_code))`.
- PATCH `/api/program-services/{id}`: `{_expected_updated_at,change_reason,name?,min_minutes?,default_minutes?,max_minutes?,default_charge_cents?,note_template_id?,active?}` → service view. Validate full merged state. Cannot activate under inactive program/facility. History GET `/api/program-services/{id}/history` → `{revisions:[...]}` admin-only, max200 then fail.

Use SQLx bound parameters, explicit same-org joins/FKs, clock_timestamp updated_at and existing ApiError mapping. Do not claim tests passed without running them (worker has no execution). Focused actual HTTP/PostgreSQL regression scenario must prove role/tenant isolation, stale edits, immutable contexts, append-only history, constraints, form-link validation, census and over-capacity reductions. Test may use explicit SQL fixtures for pre-existing active care; do not build hidden runtime fixture endpoints.

## Service routing (worker B)

Implement only `api/src/programs/services.rs` and `api/tests/program_services_postgres.rs` (root wires hooks and declares module). Functions:

`pub(crate) async fn validate_session(tx:&mut Transaction<'_,Postgres>,actor:&Actor,data:&mut Map<String,Value>,before:Option<&Value>)->Result<()>`.

`pub(crate) async fn validate_group(tx,actor,data,before)->Result<()>` with same arguments.

New sessions/groups require `program_service_id`. Session's episode must have a program matching the selected service; program and facility/service active for new booking. Validate session kind and duration in minutes against service bounds (actual elapsed time, inclusive endpoints, no rounding partial minutes into bounds). Group must use a group-kind service and facility matching its program. Client/org/episode permissions and scheduling conflict checks are handled by existing callers in addition. Copy full service row into service_snapshot on creation or genuine service change. A supplied service_snapshot is never accepted from a client; root excludes it from clean fields and only invokes these helpers afterward. When editing existing record, merge input with before. Plain status changes, attendance, cancellation, or unchanged fields must preserve the snapshot and not revalidate retired current catalog. Timing/location/clinician edits on a service-linked booking validate duration against its historical snapshot (immutable service semantics) and active program/service for new timing/assignment. Legacy bookings without a service keep ordinary historical/status handling; rescheduling requires choosing a catalog service first, then validates new program context. A service cannot be removed after assignment. Root's note/claim immutability checks remain in force.

`pub(crate) async fn enrollment_context(tx,actor,group:&Value,episode:&Value)->Result<Map<String,Value>>`: for linked group, verify same program/organization, current program/service active for new enrollment, group snapshot present and coherent, and return program_service_id + service_snapshot to copy onto the participant session. A legacy group may enroll only a legacy episode without program_id; new programs cannot silently enter unconfigured groups. Retained already enrolled attendance/status transitions remain available. Do not mutate group/client/episode or bypass capacity/schedule checks.

`pub(crate) fn claim_code_error(session:&Value,claim:&Value)->Option<&'static str>`: service-linked session requires claim.service_code to match historical service_snapshot.service_code (trim/case normalized). Missing/malformed linked snapshot blocks. Legacy session returns no catalog error. No payer eligibility or billing units are inferred; amount is a suggested default only. Test actual hooks through HTTP after root integration; include stale catalog edits preserving encounter snapshots, cross-program/tenant failures, duration bounds, retired catalog rescheduling vs completion, linked group enrollment, legacy preservation and claim code mismatch.

## Integration owned by root

New intake creation requires program_id; facility/care level derive from it. Baseline identity/consent/primary/adult checks remain mandatory, with configured min/max age and additional required intake forms. Admission revalidates active program/facility, program capacity under org lock and no overlapping same-facility/level active episode. Record immutable program/checklist evidence for ready/admitted. Discharge of a linked program checks required discharge forms for the same episode and current evidence, then existing aftercare transition; no automatic invented clinical summary.

New generic episode creation/activation is replaced with the intake route. There is no opt-out boolean or legacy mode for new care. Existing active/discharged episodes, sessions and history retain null program links until explicit assignment. Planned older episodes may be adopted into intake without overwriting original episode identity/dates. New active/discharged patient-stage writes use admission/discharge rather than direct generic edits. Existing unchanged stage updates remain compatible.

Explicit legacy assignment: POST `/api/episodes/{id}/assign-program` `{program_id,_expected_updated_at,reason,attested:true}`. Requires matching org/facility/care level, program active, age rule, and capacity if existing episode active. Preserves episode status/dates, writes one assignment event, cannot remap an assigned program. Admin/clinical lead may map active historical care; intake roles with patient scope may map planned care. Existing planned case can be assigned this way then continue its original case. New intake may accept `legacy_episode_id` to adopt an unlinked planned same-patient episode with matching facility/level/date, without creating another episode. It must not reuse an admitted/declined/withdrawn case's episode.

Root adds service selectors to real session/group booking, preserves template/fee/code snapshot suggestions in note and claim forms, maps catalog census into leadership, and integrates program requirements into form context. Tests for unrelated legacy workflows may use explicitly named SQL fixture helpers for pre-migration records; do not retain a public bypass just to satisfy old tests. New path acceptance must be genuine HTTP/UI.

Acceptance: two facilities/programs and services, exact age/date/facility routing, two concurrent admissions competing for one slot (one success), declined/withdrawn episode blocked, program edits and deactivation do not rewrite historical decisions or scheduled visit snapshots, required forms applied at admission/discharge, real service booking/group enrollment/claim-code link, explicit legacy mapping, role/tenant/stale-write protection, backups/preservation and browser walkthrough. All larger capabilities stay Partial until their full remaining scope is met.
