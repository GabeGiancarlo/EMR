# Patient identity and admission workflow contract

Implementation target for capabilities 5–7 of the expanded objective. This does not replace program configuration, clinical facesheet modules, attachments, transfer coordination, or the wider acceptance ledger. No fake patient records or content catalogs are installed. Authentication remains deferred.

## Identity and registration

Migration 018 adds a server-assigned immutable `clients.mrn`, unique within the organization, plus bounded demographic text fields `pronouns`, `preferred_language`, `address_line1`, `address_line2`, `city`, `region`, `postal_code`, `country`. Existing clients receive an identifier; their clinical history is unchanged. A database sequence supplies new identifiers. None of these fields is a clinical diagnosis or confidentiality policy.

`POST /api/intake/matches` takes `{first_name,last_name,birth_date,email,phone,exclude_client_id?}` and returns `{matches:[{id,mrn,first_name,last_name,preferred_name,birth_date,facility_id,status,reasons:string[]}],restricted_matches:boolean}`. Normalize whitespace/case for names/email and digits for phone. A possible match is equal birth date and either equal full legal name, equal nonempty email, or equal nonempty phone with at least seven digits. Never merge automatically. Only active admin/clinical_lead/clinician/support may use the endpoint. Clinicians see only primary-assigned matches; hidden matches only produce `restricted_matches:true`, without identity or counts.

Generic client creation and identity/contact-changing edits must use the same matching rules under the existing organization mutation lock. Inputs may carry `_duplicate_review:{matched_ids:UUID[],reason:string}`; this metadata is removed before ordinary record cleaning. The current matching set must exactly equal the reviewed set and the reason must contain 10–2000 characters. A clinician cannot override matches outside their panel. Missing/stale review gives 409 and preserves the attempted form. A recorded review is append-only with actor, resulting client, candidate IDs and reason. Existing unchanged demographic edits do not require retrospective review. MRN cannot be changed through API or direct UPDATE.

Root owns migration 018, `api/src/patient_identity.rs`, client route hooks, demographic fields, registration editor, identity/duplicate tests and integration. Migration 017 preserves note amendment provenance; the worker's initial source packet predates that renumbering.

## Intake cases and identity attestations

Migration 019 adds `intake_cases`, `intake_events` and `patient_identity_checks`. Every link has same-organization/patient foreign keys. Cases belong to one patient and a newly created planned episode; planned episode dates and facility are the intended admission context. Case details include owner, referral type (self/provider/facility/family/justice/other), referrer name/contact, referral reason, received_on, status, disposition reason and timestamps. No identifier-document number is collected. One nonterminal case per patient. Terminal states preserve history; no delete route.

Allowed intake roles: admin/clinical_lead/clinician/support, with primary-patient restriction for clinicians. Clinical narratives and referral contact data are not sent to billing/executive workspaces. Current active role is rechecked under the organization's mutation lock before reads and writes. Successful access/actions are audited without copying content into audit logs. Responses use no-store.

`GET /api/clients/{id}/intake` returns `{client_id,cases:[case],identity_checks:[check]}`. Each case includes `{id,client_id,episode_id,facility_id,level_of_care,starts_on,owner_id,referral_type,referrer_name,referrer_contact,referral_reason,received_on,status,disposition_reason,created_at,updated_at,checklist:[{code,title,required,passed,detail}],events:[{id,from_status,to_status,reason,actor_id,created_at}]}`. Cases are newest first, at most 100; exceeding that bound returns a clear error instead of hiding history. Identity checks are newest first, at most 100, with a returned `current` flag based on the present identity fingerprint.

`POST /api/clients/{id}/identity-checks` accepts `{method:patient_report|document_review|prior_record,outcome:confirmed|unable,reason,attested:true}`. Store an immutable attestation with actor/time and a fingerprint of the current legal first/last name, birth date and MRN. Repeating identity confirmation creates a new record. A later unable check or identity change means confirmation is no longer current. It is a local staff attestation, not verified electronic identity. Identity helper `patient_identity::fingerprint(&Value)->String` is owned by root and available to admissions code.

`POST /api/clients/{id}/intake` accepts `{facility_id,level_of_care:outpatient|iop|php,starts_on,owner_id,referral_type,referrer_name,referrer_contact,referral_reason,received_on}`. Create a planned episode and the open case in one transaction. Verify facility active, owner active in an intake role, adult eligibility using facility-local today, valid date fields and bounded text. Set the patient stage to intake only if no active episode exists. Preserve existing active care during readmission preparation.

`PATCH /api/intake-cases/{id}` accepts `{_expected_updated_at,owner_id?,referrer_name?,referrer_contact?,referral_reason?}`. Edits require current loaded version and a nonterminal case. Episode/facility/care level remain linked to their original planned episode; they cannot be reassigned by this endpoint.

`POST /api/intake-cases/{id}/transition` accepts `{_expected_updated_at,to_status:screening|ready|admitted|declined|withdrawn,reason,attested:true}`. Allowed transitions: open→screening/declined/withdrawn; screening→ready/declined/withdrawn; ready→screening/admitted/declined/withdrawn. Terminal cases cannot transition. Require a 10–2000-character reason. Append an immutable event in the same transaction as the state change.

Ready and admitted require a live checklist: eligible adult; active intended facility; active assigned primary clinician; latest identity check confirmed against current demographics; active treatment consent on facility-local today; and every active organization-authored required intake form for `any` or the selected care level signed for this exact planned episode. Signed forms must still pass transcript-source validation. Informational coverage and open-task counts may be shown separately but cannot be labeled electronically verified. Checklist details should state the missing action without claiming a legal requirement. No safety/clinical eligibility decision is automated.

Admission additionally requires active clinical role (admin/clinical_lead/clinician), intended start date no later than facility-local today, no other active episode at the same facility/care level, and a still-planned target episode. Atomically activate the episode and patient, mark admitted and append the event. Declined/withdrawn cases preserve the planned episode but must block its later activation through ordinary episode updates. Root adds a hook to prevent generic episode activation or destructive context edits when attached to an intake case; use this transition endpoint. Existing independent legacy episode workflows remain available until configurable program admission policy is implemented; the ledger must say so.

Backend worker owns ONLY migration 019, `api/src/admissions/*.rs`, and focused `api/tests/admissions_postgres.rs`. Expose `configure` and `pub(crate) async fn before_episode_update(tx,actor,before,data)->Result<()>`. Use existing records::scope/validate_links, scheduling::lock_org, access::audit, and parameterized SQLx queries. Root wires module/routes/hook and the fingerprint helper. API errors must not echo clinical text. Do not alter migrations 001–018 or unrelated modules.

## Interface

The original worker assignment owned only `frontend/src/PatientIntake.tsx`, `intakeTypes.ts`, `intake.css` and parser/state tests. That request timed out; root implemented these files locally. Final props include `clientId`, `data`, `onChanged`, `onOpenForms`, `onDirtyChange`, `onOpenConsent` and `onEditPatient`. Root mounts the staff chart Intake tab, links the exact episode to structured forms and prefills treatment consent from its checklist action.

Show the MRN and intake context, case/referral creation, current identity status with an actual attestation form, named checklist actions, owned referral details, chronological disposition history and actual allowed transition controls. Select active facilities and staff from supplied data. No automatic attestation, fabricated completion or dead buttons. A linked Form action opens the existing form workflow for that episode. Review pending forms before trying Ready. Inline errors retain typed data and explain a failed state transition. Dirty forms block parent navigation via the callback and browser unload; client changes/unmount invalidate stale responses. Use the established custom components/tokens, light/dark themes, accessible labels and narrow-screen layout. No external component package.

## Acceptance evidence required

Real PostgreSQL tests must prove stable/immutable MRNs; same-name/DOB and contact matches; no cross-tenant/panel identity leak; exact duplicate-review snapshot; optimistic edits; role checks; identity change invalidation; every readiness blocker; same-episode form completion; atomic admission/disposition events; no ordinary episode activation bypass for a linked case; and preservation of historical and ongoing care. Browser verification must perform registration→referral→identity review→required documents/consent→ready→admit using only isolated synthetic records, with a duplicate-resolution and denied-action path. The full capabilities remain Partial until their other specified modules are implemented and accepted.

## Verified checkpoint — November 2

The identity/admission implementation and custom interface are integrated locally. Migrations 018–019 add patient identity/demographic fields, append-only duplicate reviews, intake cases, disposition events and identity checks. A clinician may own an intake only for a primary-assigned patient. Staff role changes and primary reassignment cannot strand an open case outside its owner's permitted panel. Offboarding transfers open cases with an event, alongside existing assignment transfers. An incompatible replacement rolls the entire action back.

Readiness uses active organization-authored rules for the intake stage and selected level, regardless of a template's document kind. It requires a signed form for the exact episode and reuses the transcript module's current source/processing-consent validation. The UI opens that episode's form context. A signed form with an unavailable source remains historically signed but is shown as needing source review. There is no inferred medical eligibility, electronic identity verification or payer eligibility result.
