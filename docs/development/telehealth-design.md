# Encounter-linked telehealth implementation

This advances capability 12 of the expanded objective around existing individual/group encounters. [Observed checks and remaining acceptance](telehealth-checkpoint.md) distinguish the working local implementation from remote/production requirements. Identity-provider setup stays deferred. The local operator policy is not verified identity. Participant capabilities are scoped, expiring room access, not patient portal accounts.

The API owns room state, eligible participants, admission, revocation and append-only participation events. Invitation URLs contain only a random capability in the fragment. Only its SHA-256 digest is stored. Credentials never enter patient search, logs or normal browser preferences. A participant connection lease prevents a second live browser from replacing the first; reconnect after a lost browser waits for presence expiry. Guest waiting responses expose no other participants. Admission and an online host are required for peer signaling and whiteboard access. Every request rechecks room expiry, staff status and current encounter eligibility.

Browser-native RTCPeerConnection carries media directly between admitted participants. Short-lived signaling rows are polled over the existing API; SDP/ICE are never audit content or clinical notes. Peer connections are closed when admission, host presence or the current connection generation is lost. Local mode has no external ICE servers; NAT traversal needs an explicitly configured self-hosted TURN service before remote validation. No third-party video SDK or hosted AI is used.

Device capture requires an explicit participant action. Call controls mute/unmute audio/video, share the selected screen, restore the camera, reconnect, leave, and (host) end. Ending a call never resolves attendance, signs documentation or certifies billable time. A bounded collaborative whiteboard is room-scoped; it is not silently saved as a patient note. Durable media capture and consent-governed recording are the next linked capability, and will not be represented by a nonfunctional Record button.

Implementation references: [W3C WebRTC and perfect negotiation](https://www.w3.org/TR/webrtc/), [WebRTC working group negotiation sample](https://webrtc.github.io/samples/src/content/peerconnection/perfect-negotiation/), [MDN display capture and explicit user activation](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getDisplayMedia), [MDN secure contexts](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Secure_Contexts). These support API mechanics; they are not compliance certification. Real media transport passed a three-window synthetic-track check in an isolated QA harness without activating the user's camera or microphone; remote networks and actual hardware remain unverified.
